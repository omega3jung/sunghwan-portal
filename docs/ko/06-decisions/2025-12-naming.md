# 2025-12 Naming Decision

## Context

Service Desk 프로젝트를 설계하면서 **UI 컴포넌트, 폼 모드, i18n 키, 컴포넌트 API**에
일관된 이름을 사용할 기준이 필요했습니다.

특히 다음 항목의 이름과 사용 의미가 모호했습니다.

- Settings vs Preferences
- create vs edit vs view mode
- field translation key 구조
- helper function vs explicit usage
- component API (children vs trigger)

처음에는 이름을 정하는 문제로 보았지만, 점차 이름이 기능의 의미와 역할을
드러내야 한다는 점을 인식했습니다.

---

## Problem

### 1. Semantic Ambiguity

#### Example: Settings

“Settings”는 일반적으로 다음 설정을 뜻합니다.

- 시스템 전체 설정
- 관리자 설정

당시 구현하려는 기능은 다음과 같았습니다.

- 언어 변경
- 테마 변경 (light/dark)
- 컬러 테마

따라서 이 기능은 **사용자 개인 설정(User Preference)**에 해당합니다.

---

### 2. Mode Naming Ambiguity

초기 폼의 props는 다음과 같았습니다.

```ts
type?: "create" | "edit";
```

문제:

- UI가 비슷해 보여도 생성과 수정의 처리 흐름은 다름
- `edit`의 의미가 모호함
- API의 생성·수정 의도(`POST` vs `PUT`)를 명확하게 드러내지 못함

---

### 3. i18n Naming & Access

초기 고민:

```ts
t(`field.${name}.label`);
```

vs

```ts
fieldLabel(name);
```

문제:

- 도우미 함수로 감출지, 키를 직접 드러낼지 선택 필요
- 협업 시 코드 가독성 문제
- HR 담당자와 비개발자도 이해할 수 있는 구조 필요

---

### 4. Component API Naming

Dialog trigger 설계:

```tsx
<Dialog trigger={...} />
```

vs

```tsx
<Dialog>{trigger}</Dialog>
```

문제:

- flexibility vs explicitness
- API 일관성

---

## Decision Summary

```txt id="naming-core"
이름은 구현이 아니라 “의미”를 기준으로 정의한다.
```

---

## 1. Settings → Preferences

### Decision

```txt id="pref-decision"
User-facing 설정은 Settings가 아니라 Preferences로 명명한다.
```

### Rationale

- Settings = system / admin configuration
- Preferences = user personalization

### Result

```tsx
<PreferencesMenu />
```

이름으로 사용자 개인 설정 기능임을 드러냅니다.

---

## 2. Form Mode Naming

### Decision

```ts
type Mode = "create" | "update" | "view";
```

### Rationale

- edit → 모호함
- update → API semantics와 일치 (PUT)
- create/update는 필드가 같아도 **의미가 다름**

👉 와 일관성 유지

---

### Key Insight

```txt id="mode-insight"
같은 UI라도, 다른 lifecycle이면 다른 이름을 사용한다.
```

---

## 3. Explicit i18n Key Strategy

### Decision

```txt id="i18n-decision"
Helper abstraction 대신 explicit key 사용
```

### Example

```ts
t("field.title.label", { ns: "common" });
```

### Rationale

- 코드에서 번역 키의 의미를 직접 확인 가능
- 비개발자도 이해할 수 있는 표현
- 도우미 함수에 숨은 처리 제거

👉 반영

---

### Rejected Option

```ts
fieldLabel("title");
```

❌ 문제:

- 어떤 namespace의 키인지 불명확
- 도우미 함수 내부를 확인해야 실제 번역 키를 추적 가능

---

## 4. Field Naming Structure

### Decision

```json
{
  "field": {
    "title": {
      "label": "...",
      "placeholder": "..."
    }
  }
}
```

### Rationale

- label/placeholder 통합 관리
- 재사용성 증가
- 구조적 consistency 확보

---

## 5. Component API Naming

### Decision

```txt id="api-decision"
trigger prop을 기본으로 사용하되,
필요 시 children 패턴을 허용한다.
```

### Example

```tsx
<Dialog trigger={<Button />} />
```

or

```tsx
<Dialog>{trigger}</Dialog>
```

---

### Rationale

- 명시적 API 유지
- 유연성 확보

---

### Insight

```txt id="api-insight"
컴포넌트 API는 “사용 방식”이 드러나야 한다.
```

---

## 6. Naming Principle

### Rule 1

```txt id="rule-1"
이름은 구현 형태뿐 아니라 의미와 책임을 표현해야 한다
```

---

### Rule 2

```txt id="rule-2"
UI가 같아도 lifecycle이 다르면 이름을 분리한다
```

---

### Rule 3

```txt id="rule-3"
추상화보다 명시성을 우선한다
```

---

### Rule 4

```txt id="rule-4"
비개발자도 이해 가능한 naming을 지향한다
```

---

## Trade-offs

### Pros

- 의미 기반 설계 가능
- 코드 가독성 향상
- 협업 용이
- domain 이해도 상승

---

### Cons

- 다소 긴 이름
- 초기 설계 시간 증가

---

## Impact

### Code Quality

- naming만 보고도 구조 이해 가능

---

### Documentation

- 코드와 문서 간 일관성 확보

---

### Collaboration

- HR / 기획자 / 디자이너도 이해 가능

---

## Final Insight

```txt id="final-insight"
Naming은 구현 디테일이 아니라
시스템 설계를 드러내는 가장 작은 단위이다.
```

이 결정은 **도메인 중심 설계를 코드의 이름에도 일관되게 반영하기 위한 선택**입니다.

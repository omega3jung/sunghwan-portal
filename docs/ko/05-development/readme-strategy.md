# README 전략

## 목표

이 문서는 프로젝트 전반에서 README 파일을 어떻게 구성하고 배치할지 정의합니다.
주요 목표는 다음과 같습니다.

- 리뷰어에게 명확한 첫인상을 제공
- 다국어 접근성을 확보
- 확장 가능한 문서 구조를 유지
- 저장소 진입점과 심화 문서를 분리

---

## 핵심 원칙

```txt
README는 전체 문서가 아니라 진입점이다
```

루트 README는 독자가 다음 문서로 이동할 위치를 판단할 수 있도록 프로젝트,
도메인, 아키텍처, 데모, 범위에 관한 충분한 맥락을 제공해야 합니다. 이러한 영역을
요약하되 그 영역의 정규 명세가 되어서는 안 됩니다.

---

## 구조 개요

### 루트 레벨

```txt
/README.md
/README.ko.md
/docs/
```

---

## 언어 전략

### 접근 방식

각 언어는 별도의 README 파일을 가집니다.

- `README.md` -> 영어(기본)
- `README.ko.md` -> 한국어

---

### 언어 전환 섹션

루트 README 상단에는 다음과 같은 언어 전환 섹션을 둡니다.

```md
## **Languages**

- [English](../../../README.md)
- [Korean](../../../README.ko.md)
```

---

### 근거

- GitHub는 기본적으로 `README.md`를 표시합니다.
- 언어를 섞지 않아도 각 문서를 끝까지 자연스럽게 읽을 수 있습니다.
- 인라인 번역 구조의 복잡성을 피할 수 있습니다.

---

## 루트 README의 역할

루트 README는 다음 목적을 가집니다.

### 1. 프로젝트를 빠르게 설명한다

- 이 프로젝트가 무엇인지
- 왜 존재하는지
- 어떤 점이 흥미로운지

---

### 2. 핵심 설계 주제를 강조한다

예시:

- 워크플로 중심의 Ticket, Ticket Action, Ticket History, Ticket Work Session 설계
- feature, Route Handler, LOCAL/REMOTE, server-data 경계
- 승인, 할당, 초안, 첨부파일 범위
- 프로덕션 정렬 상태와 프로덕션 완성 상태의 구분

---

### 3. 더 깊은 문서로 이동할 수 있게 안내한다

```md
See more in: docs/ko/README.md
```

---

### 4. 기술적 신뢰감을 보여준다

- 기술 스택
- 프로젝트 구조
- 핵심 아키텍처 결정

---

## 루트 README 상세 경계

리뷰어가 프로젝트의 중요성과 구현된 시스템의 구성을 이해할 수 있을 만큼의
도메인 및 아키텍처 맥락을 포함합니다.

다음 내용은 중복하지 않습니다.

- 전체 워크플로 전이 또는 권한 매트릭스
- DTO, 데이터베이스 행, 필드별 계약
- 전체 운영 규칙 표
- 긴 결정 배경이나 검토 후 제외된 대안

이러한 상세 내용은 정규 명세, 현재 설계 문서, 참조 매트릭스, 결정 로그에 둡니다.

---

## README와 Docs의 관계

### 원칙

```txt
루트 README -> 리뷰어를 위한 간결한 프로젝트·도메인·아키텍처·데모·범위 요약
정규 명세와 현재 설계 문서 -> 정확한 워크플로 및 구현 규칙
결정 로그 -> 과거의 판단 근거와 대안
```

---

### 흐름

```txt
README -> docs/ko/README.md -> 상세 문서들
```

---

## Docs 구조

현재 구조:

```txt
docs/
  ko/
    01-overview/     # 프로젝트와 Service Desk의 발전 과정
    02-architecture/ # application 및 runtime boundary
    03-domain/       # 현재 domain model과 workflow rule
    04-client-engineering/ # UI, form, localization pattern
    05-development/        # 구현, 테스트, 프로젝트 공통 practice와 release 기록
    06-decisions/          # historical decision record
```

현재 설계 문서는 구현과 정렬된 시스템을 설명합니다. Development 문서에는 테스트
전략과 통합 release 기록이 포함되고, decision log는 특정 시점의 맥락을 보존합니다.
README와 overview 문서는 독자를 안내하며 적절한 source-of-truth 문서로 연결합니다.

---

### 왜 Docs를 분리하는가?

- README를 가볍게 유지할 수 있습니다.
- 문서를 확장 가능한 구조로 운영할 수 있습니다.
- 도메인 중심 설명이 가능해집니다.

---

## 이 전략이 필요한 이유

### 1. 리뷰어 경험

리뷰어, 특히 채용 과정의 평가자는 보통 다음 흐름으로 저장소를 봅니다.

1. 저장소를 엽니다
2. README를 읽습니다
3. 더 볼지 말지 결정합니다

명확한 README는 독자가 이 흐름을 따라 내용을 쉽게 파악하도록 돕습니다.

---

### 2. 관심사의 분리

- 루트 README -> 리뷰어 진입점 및 기술 요약 레이어
- 정규 명세와 현재 문서 -> 현재 시스템 설계 레이어
- 결정 로그 -> 과거의 판단 근거 레이어

---

### 3. 확장성

프로젝트가 커져도:

- README는 안정적으로 유지됩니다.
- docs는 자유롭게 확장할 수 있습니다.

---

### 4. 유지보수성

- 긴 설명을 중복해서 적지 않아도 됩니다.
- 섹션별 업데이트가 쉬워집니다.

---

## 고려한 대안

### 1. 모든 내용을 하나의 README에 담는 방식

- 장점: 단순합니다
- 단점: 너무 길어집니다
- 단점: 탐색이 어렵습니다

---

### 2. 인라인 다국어 README

- 장점: 파일이 하나입니다
- 단점: 가독성이 떨어집니다
- 단점: 유지보수가 어렵습니다

---

### 3. 별도 `readme/` 폴더 사용

```txt
/readme/README.ko.md
```

- 장점: 정리된 느낌을 줄 수 있습니다
- 단점: GitHub가 자동으로 렌더링하지 않습니다
- 단점: 첫인상이 약해집니다

---

## 결정

- README 파일은 루트 레벨에 둡니다
- 언어별 파일(`README.md`, `README.ko.md`)을 사용합니다
- 리뷰어에게 유용한 간결한 도메인 및 아키텍처 요약은 루트 README에 유지합니다
- 정확한 규칙, 매트릭스, 계약, 확장된 판단 근거는 `docs/`에 둡니다

---

## 설계 원칙과의 정렬

이 전략은 다음 원칙과 맞닿아 있습니다.

- 완전성보다 명확성
- 관심사의 분리
- 리뷰어 우선 설계
- 확장 가능한 문서 아키텍처

---

## 요약

README 전략은 다음을 보장합니다.

- 프로젝트가 강한 첫인상을 남깁니다
- 문서 구조가 계속 확장 가능합니다
- 다국어 지원이 깔끔하고 유지보수 가능합니다
- 리뷰어 중심의 기술 맥락은 루트 README에 유지됩니다
- 정규 규칙과 과거의 판단 근거는 프로젝트 소개와 분리됩니다

그 결과 저장소는 **실제로 동작하는 프로젝트**이면서 동시에
**잘 문서화된 포트폴리오 산출물**로 기능할 수 있습니다.
